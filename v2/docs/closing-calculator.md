# 마감 실적 계산기 규칙

마지막 업데이트: 2026-08-29 (라인 합계 + 소실적 기준선 규칙 구현 완료)

실적 탭(`v2/frontend/js/performance.js`)과 계산 엔진(`v2/frontend/js/performance-calculator.js`)이
따르는 규칙. 사업자와 합의해 확정한 내용이며, 테스트는
`v2/frontend/tests/performance-calculator.test.mjs`에 TC01~TC25 + 회귀 케이스로 들어 있다.

## 매출 단위

- 최소 매출 10,000원, 이후 1,000원 단위
- 1,000원 = 810 NV
- 필요 매출 = `ROUNDUP(부족NV / 0.81, -3)`
- 1,000원 단위 때문에 생긴 목표 초과 NV도 잘라내지 않고 그대로 상위에 반영한다

## 이미 구현된 규칙

1. 계산은 계보도 가장 아래 마감 사업자부터 위로 올라간다.
2. 하위 라인이 한 줄이면 본인 매출과 그 라인 전체를 비교해 대·소실적을 정한다.
3. 하위 라인이 두 줄이면 두 라인을 먼저 비교하고, **본인 매출을 기존 실적이 작은 라인에 합산한 뒤
   다시 비교해서** 대·소실적을 확정한다. 본인 매출을 처음부터 "소실적"에 넣는 것이 아니다.
4. 하위 사업자의 대실적 + 소실적 전체가 상위의 해당 서브 라인으로 올라간다.
5. 마감 사업자가 없는 일반 회원 라인은 재귀 계산 없이 현재 전체 NV를 그대로 통과시킨다.
   단 그 라인의 실제 코드에 매출을 배치하는 것은 가능하다.
6. 완료된 마감 사업자의 하위에는 중복 배치하지 않는다.
7. 가상의 회원이나 가상의 배치 위치는 만들지 않는다. 빈 라인에 넣을 코드가 없으면 마감 불가로 표시한다.
8. 최상위 목표만 입력받고 `allocateClosingTargets`가 아래로 자동 배분한다.
   하위 목표는 카드에서 직접 수정할 수 있고 "자동값으로" 되돌릴 수 있다.
9. 최상위 사업자·목표·마감 사업자 선택·하위 목표가 바뀌면 계획 서명(`planSignature`)이 달라져
   이전 완료 상태를 무효화한다.
10. 마감 취소는 그 회원과 계보상 상위의 완료만 연쇄 취소하고 형제 라인은 유지한다.
11. **상위 목표는 각 서브라인의 "라인 합계"로 내려간다.** 하위 사업자는 대·소 목표를
    따로 받지 않고 라인 합계 목표 하나만 받는다.
12. **마감 체크한 사업자는 라인 합계를 맞추면서 소실적이 지급 기준선 이상**이 되게 한다.
    체크하지 않은 라인은 라인 합계만 맞으면 그대로 통과한다.
13. 지급 기준선은 인증직급(`rankMaxName`)에서 자동으로 나온다. DT 3만 NV, GD 이상 6만 NV.
14. 부족분은 작은 줄부터 채워 두 줄이 비슷해지도록 나누고, 한 라인 금액이 크면
    코드 두 곳으로 나눠 넣는다.
15. 대·소실적은 매출을 넣은 **뒤**의 두 라인 중 큰 쪽/작은 쪽이다. 작은 줄부터 채우므로
    계산 전후로 대·소가 뒤집힐 수 있다.

## 라인 합계 + 소실적 기준선 규칙 (2026-08-29 확정 · 구현 완료)

### 배경: 옛 방식의 낭비

2026-08-28까지는 상위 목표를 하위로 내릴 때 남은 목표를 무조건 절반씩(대/소) 쪼갰다. 하위 사업자의 한쪽 라인이
이미 목표를 크게 넘긴 경우 반대쪽을 억지로 채우느라 매출이 과하게 들어간다.

실제 사례 (신주영 918875 계보):

```
신주영 918875 (본인 10,530)
├─ 신주영 918876 (본인 42,120) ─ 진순정 920633 (40,095)   → 라인 82,215
└─ 신주영 918877 (본인 89,910) ─ 이충언 928694 (8,100)    → 라인 98,010
```

- 본인 10,530은 작은 918876 라인에 합산 → 서브1 92,745 / 서브2 98,010, 라인 전체 190,755
- 상위(주영돈 2893497)가 요구하는 값은 200,000이므로 부족은 9,245뿐
- 그런데 918875·918876·918877을 모두 마감 체크하면 각자 대/소 목표가 생겨
  918877이 소실적을 50,000까지 채우느라 52,000원, 918876이 20,000원을 써서
  라인이 249,075가 되고 매출 72,000원이 들어갔다
- 올바른 결과는 부족한 9,245만 채우는 것 → 매출 12,000원, 라인 200,475
  (918875만 마감 체크했을 때. 세 명 모두 체크하면 918877의 기준선 때문에 40,000원.
  아래 "손계산 검증" 표 참고)

### 확정 규칙 (구현 완료)

1. **상위 목표는 각 서브라인의 "라인 합계"다.** 주영돈 2893496이 40만/40만이면
   2893497 라인이 40만, 2893498 라인이 40만이면 된다. 그 아래 김정경 913195와
   신주영 918875는 각각 라인 합계 20만이면 된다. 대·소를 각각 채우라는 뜻이 아니다.
2. **마감 체크의 의미를 바꾼다.**
   - 체크 안 한 사업자: 라인 합계만 맞으면 통과
   - 체크한 사업자: 라인 합계를 맞추되 **소실적이 지급 기준선 이상**이 되게 한다
3. **지급 기준선은 인증직급(`rankMaxName`)에 따라 자동 적용한다.**
   - 인증직급 DT: 소실적 30,000 NV 이상
   - 인증직급 GD 이상: 소실적 60,000 NV 이상
   - 근거는 아래 매출장려금 표
4. **기준선을 넘긴 뒤 더 채울지는 사용자가 결정한다.** 자동으로 목표까지 채우지 않는다.
   카드에 `[이대로 둔다]`와 금액 직접 입력을 둔다.
5. **부족분은 한 코드에 몰지 않고 양쪽 라인에 균형 있게 나눠 넣는다.**
   작은 줄부터 채워 두 줄이 비슷해지도록 배치하고, 기본 2곳·금액이 크면 4곳까지 내려간다.
   NV가 아니라 1,000원 단위 금액을 쪼개므로 총 매출은 한 곳에 넣을 때와 정확히 같다.
   예: 144,000원 한 번 = 72,000원 두 번 (각 +58,320, 합계 116,640으로 동일)

### 매출장려금 표 (기준선 근거)

| 직급 | 소실적 NV | 지급율 |
|---|---|---|
| DT 이상 | 3만 이상 ~ 40만 미만 | 5% |
| DT 이상 | 40만 이상 ~ 80만 이하 | 6% |
| GD 이상 | 40만 이상 ~ 80만 미만 | 8% |
| GD 이상 | 80만 이상 ~ 150만 이하 | 10% |
| RD 이상 | 150만 이상 ~ 400만 이하 | 10% |
| ED 이상 | 500만 이상 ~ 1,200만 이하 | 9% |
| DD 이상 | 2,000만 이상 ~ 3,000만 이하 | 7% |
| DD 이상 | 4,000만 이상 ~ 5,000만 이하 | 6% |
| DD 이상 | 7,500만 이상 ~ 1억 5,000만 미만 | 350만원 |
| DD 이상 | 1억 5,000만 이상 ~ 2억 미만 | 500만원 |
| DD 이상 | 2억 이상 ~ 4억 미만 | 700만원 |
| CDD 이상 | 4억 이상 | 1,000만원 |

- 인증직급 GD 이상은 소실적 6만 NV 이상일 때 지급 (표 비고란)
- 본인 매출은 소실적 매출로 인정. 단 DT·GD 승급 매출은 소실적에서 제외하고,
  승급매출을 초과한 NV는 소실적에 포함
- DT·GD 승급 매출은 본인 매출장려금에 포함되지 않음
- GD 유지 조건은 없다 (사업자 확인)

### 손계산 검증 (신주영 918875 계보)

테스트 TC21~TC23에 그대로 들어 있다. 상위 주영돈이 918875 라인에 요구하는 값은 200,000 NV.

| 마감 체크 | 결과 라인 합계 | 매출 | 비고 |
|---|---|---|---|
| 918875만 | 200,475 | **12,000원** (진순정 920633) | 문서에서 사업자가 확인한 "올바른 결과" |
| 918875·918876·918877 | 223,155 | **40,000원** (920633 12,000 · 이충언 928694 28,000) | 옛 규칙 72,000원 |
| 아무도 체크 안 함 | 190,755 그대로 통과 | 0원 | 라인 합계만 맞으면 통과 |

918875만 체크한 경우 계산 과정:

- 서브1(918876 라인) 82,215 + 본인 10,530 = 92,745 / 서브2(918877 라인) 98,010 → 합계 190,755
- 부족 9,245를 작은 줄부터 채우면 이상적으로는 7,255 / 1,990이지만
  1,990은 최소 매출 10,000원(8,100 NV)에 못 미치므로 작은 줄에 합쳐 9,245 한 번으로 넣는다
- 12,000원 = 9,720 NV → 라인 200,475

세 명 모두 체크하면 918877의 소실적이 8,100뿐이라 DT 기준선 30,000까지 21,900 NV(28,000원)를
추가로 채운다. 라인 합계만 보면 필요 없는 매출이지만, 918877에게 매출장려금을 지급하려면 필요하다.
**필요 없으면 918877을 마감 체크에서 빼면 된다.**

### 구현할 때 정한 값 (사업자 확인 필요)

1. **분산 배치 기준 금액 100,000원.** 한 라인의 추천 매출이 100,000원 이상이고 그 라인에
   넣을 수 있는 코드가 둘 이상이면 두 코드로 나눈다(라인당 2곳, 전체 최대 4곳).
   나눌 때는 NV가 아니라 **1,000원 단위 금액 자체를 반으로 쪼개므로 총 매출·총 NV는 완전히 같다.**
   예: 235,000원 → 118,000원 + 117,000원
2. **인증직급을 모르는 회원은 기준선을 적용하지 않는다(0).** 수집 JSON에 `rankMaxName`이
   없거나 "회원"이면 매출장려금 지급 대상이 아니므로 소실적을 억지로 올리지 않는다.
3. **기준선을 넘긴 뒤에는 자동으로 더 채우지 않는다.** 카드에 지금 소실적이 몇 % 구간인지와
   다음 구간까지 얼마가 남았는지를 보여주고, `[이대로 둔다]` 또는 라인 합계·소실적 최소값
   직접 입력으로 사용자가 정한다.
4. **하위 목표 직접 입력의 형식이 바뀌었다.** 예전 `{majorTarget, minorTarget}` 대신
   `{lineTarget, minorFloor}`를 쓴다. Supabase에 남아 있던 옛 형식 override는 화면을 열 때
   버리고 자동 배분값으로 되돌린다(완료 기록은 서명이 달라지면 무효화되는 기존 규칙 그대로).

## 저장 구조

- 테이블 `nrc_closing_plans` (마이그레이션 `012_closing_plans.sql`, 실행용 `RUN_012_CLOSING_PLANS.sql`)
- owner_id 기준 RLS, `(owner_id, top_member_id)` 유니크로 upsert

  사업자별 완료 대·소실적, 상위 반영 NV, 완료 상태·시각, 사용한 snapshot 정보를 저장

  이전이나 저장에 실패해도 기존 데이터를 지우지 않는다
